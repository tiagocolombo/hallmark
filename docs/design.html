Hallmark

A workshop for coding agents that runs on your machine. You hand in a request, agents build it with you, an independent principal engineer reviews it, and fixers repair what it finds. Only work that earns its hallmark leaves for GitHub. Every handoff and message is filed, so you can always see what happened and why.

The word comes from Goldsmiths' Hall in London, where silver was tested and stamped before it could be sold.

hall the command item one piece of work, prompt to PR journal the item's full history assayer the principal-engineer reviewer fixer the agent that addresses findings hallmark approval bound to a commit

Inside the Hall

Picture Hallmark as a building seen from above. Requests come in at the Front Desk, get built in the Workshop and tested in the Assay Office. If the assayer finds problems, they go to the Repair Shop and back. Approved work is stamped and leaves from the Dispatch Dock for GitHub. Every handoff passes through the Post Room, which files a copy in Records. When an item closes, the Library keeps what it taught, and briefs the principal engineer before each review (the gold slips). The boxes are items and the figures are agents.     Setup

    Hallmark ships as the hallmark package and installs one command, hall. Setup is once per machine plus once per repository.

    1. Install the binary

      Any of these puts hall on your PATH, on macOS, Linux or Windows.

      cargo install hallmark
brew install hallmark
nix profile install github:<you>/hallmark

    2. Connect Claude Code

      Installs the Hallmark plugin at user level: the skills, the reviewer and fixer agents, and the hooks. Every repo and every session gets them.

      hall setup claude

    3. Add a repository

      Run in the repo. It detects the gates, writes .hallmark.toml and a stub .hallmark/review.md for local review notes, adds a short Hallmark section to CLAUDE.md or AGENTS.md, and registers the repo.

      hall init
git add .hallmark.toml .hallmark/ CLAUDE.md
git commit -m "Adopt Hallmark"

    4. Start the daemon

      Runs the review loop for every registered repo. --at-login registers it with launchd, systemd or Task Scheduler.

      hall daemon start --at-login

    5. Check everything

      Each failed check names the command that fixes it.

      $ hall doctor
✓ git 2.51 · gh (logged in) · claude
✓ Claude Code plugin hallmark (user)
✓ hooks: SessionStart UserPromptSubmit PreToolUse
         PostToolUse Stop
✓ rindahq/platform: gates rig test, rig run build
✗ daemon not running  →  hall daemon start

    Using it

    You do three things: start work, send it to review, and check status and history. Agents do everything else. You can do all three by talking to Claude Code, or from the terminal.

    In Claude Code
    In the terminal

# start work and open Claude in its worktree
hall new "Retry failed webhook deliveries" --open
hall new --issue 212 --open

# see where things are
hall status
hall log H-0042
hall history --rejected --since 7d

# decide
hall ready H-0042
hall pull-back H-0042
hall drop H-0041 --reason "superseded by H-0044"

    On a terminal these print readable text. When an agent runs them, they print JSON.

    Where you hear about it

    • In Claude Code. In any session, in any repo, a hook tells Claude what's waiting, so it mentions it. The status line shows the count. Ask "what needs me?" and Claude runs hall inbox.
    • In the terminal app. Your Office sits at the top with a count in the title bar, and the terminal bell rings.
    • On the desktop. A notification on macOS, Linux or Windows. Clicking it opens the item in the terminal app.
    • On your phone. Through ntfy (open source, and you can host it yourself), Telegram or a Slack webhook. A question with options shows them as buttons.
    • A morning digest. One summary of what's waiting, what closed yesterday, and what it used.

    How a question travels

    1. The agent asks. hall ask "billed usage or raw events?" --options billed,raw --default billed --wait 4h. Its run ends with the status waiting, and Hallmark saves the session ID.
    2. You're told. The item moves to Your Office and the notifications go out. A reminder repeats every 2 hours until you answer.
    3. You answer anywhere. Tell Claude Code "answer H-0043: billed", run hall answer Q-12 a, press a in the terminal app, or tap the button on your phone.
    4. The agent resumes. The daemon runs claude -p --resume <session> with your answer, so the agent keeps its context. Answered within the hour, most of that context is still cached.
    5. It's on record. The question, the answer and who gave it go in the journal. Decisions worth keeping become learnings in the Library.

    If a question has a default and a wait, and nobody answers in time, the agent goes ahead with the default and the journal says so. Escalations never use a default.

    Anyone who knows the topic name can read a topic on the public ntfy.sh. Hallmark sends only the item, the question and the options, never code, and generates a random topic. You can also host ntfy yourself.

    How Claude knows to use Hallmark

    You don't need to mention Hallmark. Four things work together, from most explicit to the one that can't be skipped.

    Explicit

    /hallmark <request>

    A slash command from the plugin's skill. Always starts a new item.

    Context

    Session start

    A SessionStart hook tells Claude whether this worktree belongs to an item, what state it's in, and how to start one. hall init adds the same rule to CLAUDE.md.

    Natural language

    Skill description

    The hallmark skill's description covers starting work, picking up issues and asking about status, so "pick up #212" or "what's in review?" loads it.

    Guaranteed

    Edit gate

    A PreToolUse hook denies the first file edit or commit outside an item's worktree. The denial says exactly what to run, so Claude creates the item and carries on.

    Usage and budgets

    Every model run is measured and recorded in the journal. Each step has its own limits, and you can see totals by item, room, role, model or day. Only four places use a model: the Workshop, the Assay Office's review, the Repair Shop, and a little at the Front Desk. Everything else is a script.

    Measured

    Every run, every turn

    • Review and fix runs: claude -p --output-format stream-json reports input, output and cache tokens, turns, duration and a cost per model. Hallmark writes all of it to the journal.
    • Your Workshop session: after each turn, the Stop hook reads the new usage from the session transcript, so development counts too.
    • Checks, Post Room, stamping, shipping: scripts, no tokens. Only their time is recorded.

    Reduced

    Spend less per item

    • Checks first. A red build never reaches a model.
    • Incremental re-review. From round 2, the reviewer reads only the diff since the last round and the open findings.
    • The right model per role. Opus reviews, Sonnet fixes, Haiku summarises, and scripts handle routing.
    • Effort follows risk. A small diff gets a lighter review; paths marked sensitive in .hallmark/review.md get the deepest.
    • Fewer, larger runs. Each run starts with a fixed context cost, measured below.

    The principal engineer

    Yes, it's something you define, once, in the plugin. The role is split into a Claude Code agent (who it is and which tools it may use), a skill (how it reviews), and a schema (the exact shape of its verdict). Each repo can add local knowledge without changing the role.

    hallmark plugin
├─ agents/
│  ├─ principal-engineer.md   role, read-only tools, model
│  └─ fixer.md                edits code, can't approve
├─ skills/
│  ├─ hallmark/               your session: new, ready, status
│  ├─ principal-review/       lenses, severity, evidence rules
│  └─ hallmark-fix/           address findings, dispute with reason
├─ schemas/verdict.json       enforced output shape
└─ hooks/hooks.json           every hook calls: hall hook <event>

your repo
└─ .hallmark/review.md        local knowledge, read from base

name: principal-engineer
description: Independent reviewer for Hallmark
  items. Reviews one frozen commit against its
  base branch and never edits code.
tools: Read, Grep, Glob, Bash(git diff:*),
  Bash(git log:*), Bash(git show:*), Bash(hall log:*),
  Bash(hall library search:*)
model: opus
---
You are a principal engineer reviewing a change
you did not write. Use the principal-review skill.
Report only what you can show breaks, with the
scenario. Approve when nothing blocks.

    The daemon runs it headless with a fresh context. --json-schema makes Claude Code return a verdict that always matches the schema, so the daemon never has to parse prose.

    claude -p --plugin-dir "$HALLMARK_PLUGIN" --agent principal-engineer \
  --json-schema "$HALLMARK_PLUGIN/schemas/verdict.json" \
  --output-format stream-json --verbose \
  "Review H-0042 round 2: commit b81f3e4 against main"

    This is a sketch; the exact flags will be checked when it's built. Everything the reviewer reads comes from the base branch, so a change can't edit its own review rules.

    The Library: what the principal engineer remembers

    Each review starts with a fresh context on purpose. A long-lived reviewer would carry the biases of earlier reviews, and its growing context would be re-read on every call; this conversation alone has read 18M tokens from cache. Instead, the reviewer starts clean and gets a short briefing from the Library, a growing body of what reviews of this repository have taught. Fresh eyes, long memory.

    How it learns

    1. An item closes or escalates. Its journal holds what the reviewer found, what was disputed and how it was settled, and your decisions with reasons.
    2. The librarian distils it. A small Haiku run turns the journal into proposed learnings. It updates existing entries rather than adding duplicates. Each costs a few thousand tokens.
    3. You approve the learnings. Proposed learnings wait in your inbox until you accept or reject them with hall library review. They live in a local store next to the journal, never in the repository, so no branch can change what its review is told.
    4. The reviewer is briefed. Before each review, Hallmark picks the learnings scoped to the changed paths and searches the rest using the diff. It sends the best of them within a set token limit.
    5. Learnings earn their place. Each verdict says which learnings it used and whether they held. Contradicted or unused ones are retired.

    Where qmd fits

    qmd is a local search engine for Markdown, built for agents. It combines keyword search, vector search and reranking, with local models stored in SQLite. It has a JSON command line and an MCP server, and it's MIT-licensed. The Library is a folder of Markdown files, so qmd fits it without changes. It also runs locally, so searching the Library costs no Claude tokens.

    It brings a Node 22 or Bun runtime, about 2 GB of local models, and on macOS a Homebrew SQLite. That's a lot to require of every install, so Hallmark makes it an option. Built-in search works everywhere; hall init offers qmd when it finds it. Hallmark always queries a single collection, because qmd ranks results from several collections in one shared pool.

    # .hallmark.toml
[library]
search         = "qmd"     # or "builtin"
collection     = "hallmark-platform"
briefing_limit = "6k"      # tokens sent to each review
auto_accept    = ["map"]   # kinds that skip your approval
retire_after   = "90d"     # unused learnings

    Built for agents

    Agents are the main users of hall, so the command line is an API. These rules hold for every command.

    • JSON when it isn't a terminal. --json forces it; readable text appears only on a terminal.
    • Never prompts. Anything destructive needs an explicit flag, such as --reason.
    • Safe to repeat. Running hall ready twice returns the same review, not an error.
    • Says what to do next. Every reply has a next list of commands that make sense now.
    • Errors are data. A stable code, a message and next, plus a documented exit code.
    • Describes itself. hall help --json lists commands; hall schema <command> gives the output shape.
    • Knows where it is. Inside an item's worktree the ID is optional.
    • One worker per item. hall next --role fixer claims work with a lease, so two agents never take the same item.

    The terminal app

    One Rust binary, hall, does everything. Run it with no arguments and it opens the terminal app, the human view of everything above. The subcommands are what agents, hooks and the daemon call. Because the hooks call the binary rather than shell scripts, it runs the same on macOS, Linux and Windows.

    The app only reads the journal. Closing it never stops work; the loops run in hall daemon. Opening it on another terminal, or after a restart, shows the same state.

    Views
    • Board. Items by state, with ones that need you flagged at the top.
    • Journal. The selected item's full history, newest at the bottom, with a scrubber to replay it as above.
    • Findings. Every finding with its lens, severity, file and line, the commit that claims to fix it and the review that verified it.
    • History. Closed and dropped items, filterable by outcome, lens or rejection reason. It answers "what got rejected this week, and why".
    • Live. The output of whatever the daemon is running now: a test run, or the reviewer's progress.
    • Usage. Tokens and API-equivalent cost by room, item, model or day, against your budgets.
    • Repos. Every repository on this machine that uses Hallmark, with counts of items needing you. tab switches between them.

    The journal

    Each item has an append-only file of events. Nothing is edited or deleted, so the history you read is the history that happened. Hooks write your session's events and the daemon writes the loop's. Every write goes through hall, which holds a file lock.

    .git/hallmark/                  shared by every worktree
├─ items/H-0042/
│  ├─ item.json              title, branch, state
│  ├─ events.jsonl           the journal
│  ├─ reviews/r1.md          full review reports
│  ├─ checks/r1.log          failing check output
│  └─ runs/                  each headless run, streamed live
└─ queue/                    tickets waiting for the assayer

    A SQLite index, rebuilt from these files at any time, answers usage and history questions quickly. The journal lives in each repo's git directory, so it outlives worktrees and is never committed. A small registry in your user state directory lists which repos use Hallmark, so the terminal app can show them all. hall export H-0042 writes the whole record as Markdown, and the review comment on the PR points to it.

    How the assayer reviews

    Every review covers the same seven lenses. Each finding names its lens, a file and line, a severity, and the concrete case that breaks.

    LensAsksTypical blocker
    First principlesIs this the simplest change that solves the task? Does it belong in this layer?Patches a symptom; duplicates an existing mechanism
    CorrectnessEdge cases, error paths, concurrency, idempotency, retriesA retry double-charges; two writers race
    Security & tenancyAuthorization on every path, tenant isolation, secrets, injectionA query bypasses RLS; a secret in a log line
    Data & migrationsIs the migration reversible and safe on live data?A locking ALTER on a hot table
    EvidenceDo the tests prove the behaviour? Did the test count drop?A test asserts its own mock; a suite stopped compiling
    OperabilityCan someone on call see it fail and recover?A swallowed error on a billing path
    Repo rulesThe repo's CLAUDE.md or AGENTS.md and any rule files it listsBreaks a convention the repo wrote down
    blockermajorminornit approve = 0 blockers and 0 majors

    Rules come from main

    The assayer loads its skill and lenses from the base branch, never from the branch under review, so a branch can't soften its own review.

    Approval is bound to a commit

    The hallmark is a git note on one SHA. Any later commit has none, so the gate blocks it until it is reviewed again.

    A script decides when to stop

    Loops end when the hallmark exists or the round limit is reached, never because an agent printed "done".

    Before building

    Why it's worth it

    • Parallel agents in many worktrees, across many repos, get one place to be seen.
    • It uses your Claude plan and your choice of model, with no API tokens and no Copilot seat.
    • The journal answers questions that are hard now: why something was rejected, what changed between rounds, how long review takes.

    What to watch

    • Same model, same blind spots. Fixed lenses and checks help, but keep the final merge on GitHub with you.
    • Shared state. Test runs often share caches, coverage files and ports, so each repo's assayer takes one ticket at a time. Separate repos can run in parallel.
    • Usage. Every round is a test run plus a long review against your plan's limits. Three rejected reviews send the item to you.
    • The journal records your prompts. It stays in .git/hallmark/ on your machine and is exported only when you ask.

    Works in any repository

    Hallmark assumes only git and Claude Code. Everything specific to a project lives in one optional file at the repo root, and hall init writes a first version of it by looking at the repo.

    Install once

    The binary, the /hallmark and principal-review skills and the hooks ship as one Claude Code plugin. Hooks are installed at user level, so every repo and every session gets them.

    hall init

    Detects the stack and proposes the gates: package.json scripts, cargo test and clippy, go test and go vet, pytest, a Makefile, or a justfile. It also finds CLAUDE.md or AGENTS.md for the repo-rules lens.

    Sensible defaults

    With no config, worktrees use git worktree add, shipping uses git push and gh pr create, and the review uses all seven lenses. A repo on GitLab sets the ship command to glab mr create.

    Defaults, used when a key is missing
    # .hallmark.toml
base         = "main"
worktree     = "git worktree add ../{repo}-{id} -b {branch}"
ship         = "git push -u origin {branch} && gh pr create --fill"
gates        = []                  # hall init fills these
reviewer     = "claude -p"
max_rejects  = 3
stuck_after  = "30m"
lenses       = "all"
rules        = ["CLAUDE.md", "AGENTS.md"]

[budget]                           # runs are capped by default; daily caps only if you set them
review_model = "opus"
fix_model    = "sonnet"
    Example override: rindahq/platform
    # .hallmark.toml
worktree = "rig wt new {branch}"
ship     = "rig submit --pr"
gates    = ["rig test", "rig run build"]
rules    = ["CLAUDE.md",
            "docs/plan/README.md#leave-alone"]

    Every command is a setting, so a repo can use its own tooling without Hallmark knowing about it. The reviewer and fixer commands are settings too. Claude Code comes first because its hooks and skills make the session part of the record.

    Build order

    Stage 1

    Journal and hooks

    The hall binary with the agent contract, setup claude, init, doctor, items, the journal, the hallmark skill, the session hooks and the gate. Everything you do is recorded from day one.

    Stage 2

    The review loop

    The daemon, the principal-engineer and fixer agents with their skills and verdict schema, hallmarks, pull-back and issue linking, then the Library with built-in search and the librarian.

    Stage 3

    Terminal app and plugin

    The board, journal, findings, history, usage and live views, qmd as an optional Library search, then packaging as a plugin with cargo-dist releases for macOS, Linux and Windows.
