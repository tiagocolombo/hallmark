# Hallmark 0.4: the software factory

Status: Proposed plan, 2026-11-28. Nothing here is built yet. Each decision
below becomes an ADR before its milestone starts (see
[ADRs to write](#adrs-to-write)), and each piece of work becomes items.

## The goal

Hallmark 0.3 is a review loop that lives inside a git repository and inside
Claude Code. 0.4 makes it a **software factory you run from a browser**:

- **It runs by itself.** You install `hall` and open it. No repository, no
  prior setup, no terminal knowledge is needed to start.
- **Projects, not repos.** You start a project from scratch or bring an
  existing folder or repository. It can stay on this computer and be
  connected to GitHub later, or go to GitHub from the start.
- **A tracker, like Jira.** Requests become stories with acceptance
  criteria, priorities, estimates and dependencies, on a backlog and a board.
  Grooming happens in the page: the Product Manager's questions, your answers,
  your priorities.
- **Any harness, any model.** The loop is Hallmark's. The agents that plan,
  build, review and fix are pluggable: Claude Code, Codex, Gemini CLI or
  Antigravity, or any model behind an API key, including local ones.
- **The web app runs everything.** Setup, intake, grooming, building,
  review, shipping, settings, budgets. The CLI stays the API underneath
  (ADR 0002), so agents and scripts keep everything they have today.

### The first ten minutes

```text
1. Install       curl …/hallmark-installer.sh | sh      (or the PowerShell line)
2. Open          hall                                     → the browser opens on Welcome
3. Your machine  git ✓   an agent: Claude Code ✓ / Codex ✗ / an API key …
4. Project       New "recipe-box" · template Web app · "Keep it on this computer"
5. Your idea     a short brief, then a list of requirements, pasted as they are
6. Grooming      8 stories with criteria and priorities, 2 questions → answered
7. Backlog       ranked; "Start" on the first one
8. Building      the builder works in the background; you watch it on the board
9. Review        checks, then an independent reviewer, then fixes, then a hallmark
10. Done         merged into the project locally; "Save to GitHub" whenever you want
```

## Principles

1. **The CLI is the API; the web is the product.** Every button runs a hall
   command (ADR 0052), every command keeps the agent contract (ADR 0002). A
   person should never *need* the terminal.
2. **Hallmark owns the loop; agents are adapters.** Nothing about the states,
   the journal, the gates, the verdicts or the hallmark depends on which
   agent ran. A harness or an engine only fills in a role.
3. **Guarantees live in layers every agent passes through:** git, the
   hall CLI, MCP. A harness's own hooks add capture, never the only lock.
4. **Local first.** Git always runs underneath, but a remote is optional.
   GitHub adds delivery; it is not required to finish an item.
5. **Plain words for beginners, full power for pros.** No git vocabulary on
   the happy path ("Save to GitHub", not "push origin"); every advanced
   setting is still one click (or `hall config`) away.
6. **The journal stays append-only** (ADR 0003, 0008). New tracker
   concepts are new events folded through `state::next`.

## 0.3 → 0.4 at a glance

| | 0.3 | 0.4 |
| --- | --- | --- |
| Starting point | `cd repo && hall setup` | `hall` opens the web app; a project is created or added there |
| Where work lives | a git repo you already have | a project: new from a template, an existing folder, or a GitHub clone |
| Models | `claude -p` for every run (ADR 0006) | an engine per role: Claude Code, Codex, Gemini CLI, or the built-in engine with any API model |
| Development sessions | Claude Code with the plugin's hooks | any harness: git hooks and `hall mcp` for everyone, native hooks where a harness has them |
| Planning | the PM and the Lead inside `hall new` (ADR 0068 step 1) | `hall plan` over a list, a backlog, grooming questions, ranks, `hall start`, a WIP limit |
| Who builds | you, in Claude Code | the builder worker in the background, or you in your harness |
| Shipping | a PR on GitHub | merged locally, or a PR on GitHub; `hall connect github` at any time |
| Web app | a reader with actions for one registry of repos | the main interface: onboarding, board, backlog, story pages, agents and settings |

## 1. Engines: headless runs with any agent

Today `runner.rs` builds one command shape, `claude -p … --output-format
stream-json --json-schema …`, and `usage.rs` parses its result. The
`Runner` trait (`src/runner.rs:456`) and the `FakeRunner` are the seam.

**Decision (ADR 0076): the runner becomes an engine interface with
adapters.**

- An **engine** takes a `RunRequest`: role, instructions, prompt, working
  directory, tool access (`read` or `write`), a JSON Schema for the answer,
  a timeout, a budget, an optional session to resume. It returns a
  `RunOutcome`: the structured answer, usage, a session id, how it ended.
- Each adapter turns its harness's output into **hall's own trace lines**
  (`hall schema trace-line`), so `hall trace`, the web app's live runs and
  the Gazette don't care which engine ran.
- Adapters in 0.4:

| Engine | Runs | Structured answer | Sandbox | Notes |
| --- | --- | --- | --- | --- |
| `claude` | `claude -p` (today's shape, unchanged) | `--json-schema` | Claude Code's sandbox settings (ADR 0053) | the reference adapter; snapshots must not change |
| `codex` | `codex exec` with JSON events | its output-schema option | its own sandbox modes | to confirm in the spike |
| `gemini` | Gemini CLI headless | schema in the prompt, validated by hall | its own sandbox | to confirm in the spike |
| `builtin` | hall's own small agent loop over an API | a final `answer` tool, validated against the schema | read-only roles only in 0.4 (below) | any model: OpenAI-compatible APIs (OpenAI, OpenRouter, Ollama, LM Studio, vLLM…), Anthropic, Gemini |
| `fake` | the scripted runner | as today | — | tests never spend usage |

- **Roles pick an engine and a model.** `[roles.<role>] engine, model,
  effort, max_usd, timeout` for `pm`, `intake` (the Lead), `builder`,
  `reviewer`, `verifier`, `security`, `fixer`, `librarian`. Today's keys
  (`review_model`, `fix_model`, `intake_model`, `[budget.review]`…) keep
  working as aliases for the `claude` engine. A model can be written
  `engine:model` anywhere a model is asked for.
- **Agents and skills become prompt packs.** `plugin/agents/*.md` and
  `plugin/skills/` are rendered per engine: as a Claude Code plugin agent
  (today), as the system prompt for `builtin`, and as instructions plus the
  repo's `AGENTS.md` for `codex` and `gemini`. Schemas in `plugin/schemas/`
  stay the single definition of every answer.
- **Independent review across vendors.** Setup suggests a reviewer on a
  different engine than the builder (built by Codex, reviewed by Claude, or
  the reverse). An independent reviewer is Hallmark's whole idea, and a
  reviewer from another vendor is more independent still.
- **The built-in engine writes nothing in 0.4.** Read-only roles (PM, Lead,
  reviewer, verifier, security, librarian) need `read`, `grep`, `glob` and a
  few git reads, which hall can confine to the checkout itself. Writing roles
  (builder, fixer) run arbitrary commands, which needs an OS sandbox; until
  hall has one (a later ADR), they run on a harness that brings its own
  sandbox, or on `builtin` only with `[sandbox] mode = "off"`, set on
  purpose and shown as a warning everywhere.
- **Usage and cost per engine.** Each adapter reports tokens by kind. The
  price table (`usage::price`) gains a `[prices]` override for models it
  doesn't know; an unknown model is counted in tokens and shown without a
  dollar figure. Budgets (ADR 0016) are unchanged.
- **Limits and failures.** "Out of usage" and "rate limited" are detected
  per adapter and become the same pause as today (ADR 0055, the limit
  pause).
- **Keys.** API keys for `builtin` live in the OS keychain (the `keyring`
  crate), entered in the web app or with `hall engines key set <provider>`,
  never in `.hallmark.toml` or the journal, and never passed to a sandboxed
  run's environment.
- **Choosing by evidence.** `hall eval` (ADR 0065) gains `--engine` and
  `--model`, so an engine is picked for the reviewer by its score on your own
  reverted PRs, not by its reputation.

## 2. Harnesses: development sessions with any agent

Today everything a development session does is seen through Claude Code's
hooks (`plugin/hooks/hooks.json` → `hall hook <event>`): binding a session
to an item, recording prompts and turns, gating edits, gating pushes
(`gate.rs` parses Bash), and resuming a session with an answer.

**Decision (ADR 0077): the guarantees move to layers every harness passes
through; native hooks only add capture.**

1. **Git hooks.** `hall init` sets `core.hooksPath` to a hall-managed
   directory whose hooks only call `hall hook git-<event>`
   (`pre-commit`, `post-commit`, `pre-push`; each a one-line `sh` stub,
   which Git for Windows runs too). The push gate and commit recording then
   hold for every harness and for a person at a terminal. A repo's existing
   hooks are chained, not replaced.
2. **`hall mcp`.** An MCP server over stdio with the agent's commands as
   tools: `new`, `plan`, `status`, `findings`, `propose-ready`, `ask`,
   `attach`, `threads`. Claude Code, Codex, Gemini CLI and Antigravity all
   speak MCP (Antigravity to confirm in the spike). It is the same contract
   as the CLI, so it's a thin layer.
3. **Instructions in every dialect.** One source (today's `hallmark`
   skill) renders the section `hall init` writes into `CLAUDE.md`,
   `AGENTS.md` and `GEMINI.md`, whichever the project uses, plus the
   harness-specific rules file where one exists.
4. **Native hooks where a harness has them.** Claude Code keeps today's
   plugin. Gemini CLI and Codex get adapters if their hooks cover prompts,
   turns and tool calls (spike). They add prompt capture, the edit gate
   (`[capture] mode = "gate"`) and session binding.

What each harness gets:

| | Claude Code | Codex CLI | Gemini CLI | Antigravity | Any other editor / a person |
| --- | --- | --- | --- | --- | --- |
| Push gate | ✓ native + git | ✓ git | ✓ git | ✓ git | ✓ git |
| Commits recorded | ✓ | ✓ git | ✓ git | ✓ git | ✓ git |
| hall tools | ✓ CLI + MCP | ✓ MCP | ✓ MCP | MCP (spike) | CLI |
| Prompts and turns recorded | ✓ | if hooks allow (spike) | if hooks allow (spike) | — | — |
| Edit gate before an item exists | ✓ | if hooks allow | if hooks allow | — (git catches it at commit) | — (git) |
| Resumed with an answer | ✓ `--resume` | `codex exec resume` (spike) | spike | — (inbox notice) | — |

Where a harness can't be gated before an edit, the post-commit and
pre-push hooks catch the work instead: commits made outside an item are
offered for `hall adopt` from the inbox, and nothing is pushed without a
hallmark.

**Setup.** `hall setup <harness>` (`claude`, `codex`, `gemini`,
`antigravity`) installs what that harness takes: the plugin, the MCP entry,
the rules. `hall doctor` and the web app's *Agents* page detect which
harnesses are installed and signed in.

## 3. Projects, not repos

**Decision (ADR 0078): a project is a registered folder that hall can
create, adopt or clone; git runs underneath, a remote is optional.**

- `repos.json` becomes the **project registry**: name, path, mode
  (`local` or `github`), template, created by hall or adopted. Existing
  entries migrate as adopted projects.
- `hall project new <name> [--path] [--template] [--github private|public]`
  creates the folder, runs `git init` (with a local fallback identity, or
  the GitHub noreply address as rig does), applies the template, runs
  `hall init` and registers it. `hall project add <path>` adopts a folder
  (running `git init` if needed, after asking in the web app) and
  `--clone <owner/repo>` clones first. `hall project list|remove|rename`.
- **A projects root,** `~/Hallmark` by default (`hall config set --user
  projects.root`), where new projects go unless a path is given. The web app
  only creates folders inside it, or in a folder the person picked.
- **Templates are embedded** like the plugin: `blank`, plus a few stacks to
  start, each with its gates, `.hallmark.toml`, rules files, a `.gitignore`
  and the sandbox domains its package registry needs. Taken from rig's
  `templates/` idea; with `nix` on the machine, a template can also write a
  `rig.toml`/`flake.nix` toolchain, off by default.
- **An empty project is planned differently.** A project brief
  (`docs/brief.md`: what it is, for whom, constraints, stack preference) is
  written in onboarding and read by the PM. On a repository with no code, the
  Lead's first decision is a foundation item, or a spike that chooses the
  stack and writes a design note (ADR 0075).
- `NOT_A_REPO` and `NOT_INITIALIZED` hint at `hall project new` and
  `hall project add` instead of only `git init`.

## 4. The tracker

ADR 0068 already designed most of it; step 1 is built. 0.4 finishes it and
adds what a tracker needs on top.

| Jira | Hallmark | Status |
| --- | --- | --- |
| Epic | a plan (`P-0003`) or a parent item with slices | plans: proposed in 0068 |
| Story | an item, with its story, criteria, priority, estimate | built (criteria, priority) |
| Sub-task | a parallel part (ADR 0024) | built |
| Backlog | the `backlog` state, ranked | proposed in 0068 |
| Status | the item's state, grouped into board columns | built |
| Priority | `now` / `next` / `later`, the PM's or yours | built (PM); `prioritize`: proposed |
| Rank | the order inside a priority | **new**: `ranked` event |
| Estimate | weighted tokens (ADR 0016) | proposed in 0068 |
| Dependencies / links | `after`, follow-ups, merges | proposed in 0068 |
| Assignee | the engine and harness that build it, or you | **new** |
| Comments | threads (ADR 0070), plus **your comments** | **new**: `commented` event; a comment on a live item reaches its next agent (ADR 0044) |
| Labels | free labels | **new**: `labeled` event |
| Attachments | `hall attach` (ADR 0053) | built |
| Activity | the journal | built |
| Sprint | not in 0.4: the WIP limit and the queue do this work | — |

Work for 0.4:

- **ADR 0068 steps 2 onward:** `hall plan` over a list (file, stdin or
  the page), plan journals, the `backlog` state, `hall plan answer`,
  `prioritize`, `apply`, `hall start`, `[plan] wip`, grooming questions in
  the inbox, re-planning held stories after answers.
- **New events:** `ranked`, `commented`, `labeled`, `assigned`, folded
  like the rest; `hall rank`, `hall comment`, `hall label`, `hall assign`.
- **`hall board`:** the whole board in one reply (columns, cards, counts,
  WIP), so the web app draws it from one command.
- **Import, later:** GitHub issues stay (`--issue`). Jira and Linear
  import or sync is an issue-source adapter for 0.5, not 0.4.

## 5. The factory runs from the web

- **The builder worker.** A started item no session claims is built by a
  headless development run on the `builder` role's engine, in its worktree,
  with the item's story, criteria, the repo's rules and skills, and the
  Library's briefing. It commits as it goes, asks with `hall ask` when it
  must (the question lands in the inbox and on the card), and ends with
  `hall propose-ready`. The same sandbox and budgets as the fixer apply. The
  delivery worker's headless dev runs are its starting point.
- **Or build it yourself.** A card's *Open in…* gives the command (or
  launches it, where the OS allows) that opens the worktree in your
  harness: `claude`, `codex`, `gemini`, Antigravity, or your editor. A
  session that binds to the item takes it over from the builder; the
  builder stops at its next step.
- **Autopilot levels per project:**

| Level | Starts items | Says "ready" | Merges |
| --- | --- | --- | --- |
| Manual | you | you | you |
| Assisted (default) | you | the agent, when nothing is left to confirm | you |
| Autopilot | the backlog, within the WIP limit | the agent | the merger (ADR 0048), or locally |

## 6. The web app

**Decision (ADR 0079): the web app becomes the main interface; it stays
local, embedded and offline.**

Screens:

- **Home:** your projects, each with what needs you, what's moving, today's
  spend; *New project*.
- **Welcome / onboarding:** the machine check, the first project, the
  brief, the first requirements, grooming, the first start. Every step can
  be left and resumed.
- **Board:** Kanban by stage (Backlog · Building · Checks · Review ·
  Fixing · Hallmarked · Shipped · Done), drag to start, rank or drop (with a
  reason); swimlanes by epic or priority; filters by label, engine, state.
- **Backlog and grooming:** the ranked list, epics, estimates and
  dependencies; open questions with their answers; *Add requests* (one or
  many, pasted as they are) → a plan to review → *Apply*.
- **Story page:** story, criteria (ticked as evidence arrives), comments
  and threads, activity, attachments, live run, diff, findings, checks,
  cost, PR, Gazette, and the actions that fit its state.
- **Factory floor:** today's animated rooms, live.
- **Inbox:** what needs you, with one-click answers.
- **Agents:** harnesses found and signed in, engines and keys, which engine
  and model each role uses, the reviewer eval scores.
- **Settings:** project (gates, how work ships, autopilot, WIP), GitHub,
  budgets, notifications, extensions, the daemon, doctor, updates.

How it's built:

- **Still every call a hall command** (ADR 0052), with the allowlist
  widened to `project`, `plan`, `start`, `rank`, `comment`, `label`,
  `assign`, `connect`, `setup <harness>` and `engines`. Folder creation is
  limited to the projects root or a picked folder; GitHub actions ask for
  confirmation in the page.
- **Live, not polled:** `GET /api/events` (server-sent events) tails the
  journals and run streams and tells the page what changed; it then reads
  the commands it needs.
- **Still no build step and no network.** A Jira-class UI is past what
  hand-written DOM code holds well (`app.js` is 1,468 lines already). Vendor
  a small component library that needs no compiler (Preact with htm, about
  10 kB) into `src/web/assets/`, embedded as today, instead of adding a
  Node build to a Rust project. (A decision to confirm.)
- **Friendly by default:** every empty state says what to do next; errors
  show the `message` and turn `next` into buttons; plain words on the happy
  path; keyboard shortcuts for people who want them; light and dark.

## 7. Install and first run

- The installers stay (cargo-dist). After installing, they print one line:
  `hall` to open it.
- **`hall` outside a project** opens the web app on Home or Welcome when
  there's a browser, and the terminal app's project list otherwise. (Today
  it prints status as JSON off a TTY; that doesn't change.)
- **`hall doctor` works outside a repository:** git, at least one
  harness or engine key, gh (only when GitHub is used), the daemon, the
  projects root. Each failure names its fix; in the web app, a button where
  hall can fix it, a copyable command where it can't.
- **The lowest bar:** with no harness installed at all, a person can paste
  an API key and run every read-only role on `builtin`, and build on the
  first harness they install. Installing git for them (Xcode command-line
  tools, `winget`) is offered, not assumed.
- The daemon starts at login once the first project exists (`hall daemon
  start --at-login`, as `hall setup` does today).

## 8. Local, then GitHub

**Decision (ADR 0080): shipping has a target, `local` or `github`.**

- **Local.** A hallmarked commit is merged into the project's base locally
  (fast-forward, or a merge commit when the base moved), and only when the
  hallmark note verifies, as the push gate checks it (ADR 0045). The
  Delivery Office, the merger, the CI watch and the reverts worker stay idle.
  The item closes as *merged*. No `gh` needed.
- **`hall connect github [--create private|public] [--repo owner/name]`.**
  Signs in with `gh auth login --web` (the page shows the one-time code),
  creates or links the repository, pushes the base, switches `ship`,
  `update`, `review_comment` and `merge` to their GitHub defaults, and turns
  delivery on. In the page it's *Save to GitHub*, and it always asks first,
  since it publishes code.
- Moving back to local, or to another host later, is a change of target;
  the journal keeps both chapters.

## Migration from 0.3

- Existing repos keep working with no change: they appear as adopted
  projects with target `github`, engine `claude` for every role, harness
  `claude`.
- Old config keys stay valid as aliases; `hall config` writes the new ones.
  `hall doctor` lists the aliases in use, as a note, not a failure.
- `hall init` on an existing repo adds the git hooks (chaining any it
  finds) and the MCP entry; `--no-git-hooks` leaves git alone.
- `docs/install.md` gets an *Upgrading to 0.4* section; the CHANGELOG lists
  every renamed key.

## Risks

- **Harness drift.** Codex, Gemini CLI and Antigravity change fast and
  their headless and hook interfaces are younger than Claude Code's. The
  fixtures from M0 and an adapter test suite per engine are the defence;
  `hall doctor` checks a harness's version against the range we tested.
- **Quality varies by model.** A cheap model as reviewer can approve bad
  work. Defaults stay conservative (a strong reviewer), the reviewer eval
  shows the difference on your own history, and the Agents page shows it.
- **The built-in engine is a new agent.** Keeping it read-only in 0.4 keeps
  its blast radius small; writing comes with a real sandbox, later.
- **The web app widens what the token can do.** Creating folders, adding
  keys and publishing to GitHub from a page. Constrained paths, confirmation
  for anything outward-facing, keys never returned to the page after entry,
  and the existing token and Host checks (ADR 0052).
- **Windows.** Git hooks through Git for Windows' `sh`, keychain access,
  launching harnesses, template gates through `cmd /C`. CI on Windows
  remains the check.
- **Scope.** This is the largest release so far. The milestones are
  ordered so each one ships value on its own if 0.4 has to be cut short:
  M1 and M2 alone make Hallmark harness agnostic for today's users.

## Open decisions

1. **Web UI technology:** vendored Preact and htm with no build step
   (recommended), or a compiled frontend.
2. **Which harnesses are first-class in 0.4:** Claude Code and Codex fully,
   Gemini CLI and Antigravity at the git and MCP level until their spikes
   say more (recommended), or all four fully.
3. **Default projects root:** `~/Hallmark` (recommended), or rig's
   `~/src/github`.
4. **Templates to ship first:** `blank` plus which stacks.
5. **Jira or Linear sync:** out of 0.4 (recommended), or in.
