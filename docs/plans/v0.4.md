# Hallmark 0.4: the software factory

Status: Proposed plan, 2026-11-28. Nothing here is built yet. Each decision
below becomes an ADR before its milestone starts (see
[ADRs to write](#adrs-to-write)), and each piece of work becomes items.

## The goal

Hallmark 0.3 is a review loop that lives inside a git repository and inside
Claude Code. 0.4 makes it a **fully automated software factory**, run from a
browser, for developers and for people who have never written code:

- **From scratch or from what you have.** Start a new project from an idea,
  or bring an existing folder or repository and keep building on it.
- **The PM and the Lead run the floor.** They are the orchestrators: they
  know everything going on, talk to you, and hand out work. Every other role
  works on one unit of work with a short, focused context, and asks the
  others through its own inbox, a Q&A board like Stack Overflow. Everything
  is logged.
- **A crew of agents does the work.** A Product Manager turns requests into
  stories, a Lead plans them against the board, an Architect designs what's
  new, a Builder builds, an independent Reviewer reviews, a Fixer fixes, and
  the Librarian keeps the project's memory. You are the stakeholder: you say
  what you want, answer questions, and accept what's built.
- **You talk to the PM and the Lead, never around them.** On any issue
  that isn't finished, you can ask, add context, change your mind or ask for
  more; they decide how: answer, change the issue, or create a new one.
- **One front door.** Every request, at any time, goes through the PM and
  the Lead: the first idea, the hundredth feature, a bug, a list of issues
  copied from another tool, a change you ask for after trying a story.
- **It remembers.** A project memory (product, architecture, decisions,
  what's built) is kept up to date after every item and briefed to each
  agent, so the PM doesn't relearn the project for every request.
- **Any of the big three, or any model.** Claude, OpenAI and Google Gemini
  are first class, through their harnesses (Claude Code, Codex, Gemini CLI)
  or their APIs; any other model works through an OpenAI-compatible API.
- **A board that works like Linear.** Issues with criteria, priorities,
  estimates and relations, a backlog and a board; fast, keyboard-first, with
  views, filters and a command palette. Hallmark's own tracker: no sync with
  Linear, Jira or GitHub is needed.
- **The web app runs everything.** Setup, requests, grooming, building,
  review, previews, shipping, memory, settings, budgets. The CLI stays the
  API underneath (ADR 0002), so agents and scripts keep everything.

### Two first sessions

**Someone with an idea and no code:**

```text
1. Install       curl …/hallmark-installer.sh | sh      (or the PowerShell line)
2. Open          hall                                     → the browser opens on Welcome
3. Your machine  git ✓   agents: Claude ✓  OpenAI ✗  Gemini ✓   (or paste an API key)
4. Project       New "recipe-box" · "Keep it on this computer"
5. Your idea     who it's for, what it does, anything you already know
6. Grooming      the PM: 9 stories with criteria, 2 questions → you answer
                 the Lead: a foundation item first, then 3 slices; the Architect picks the stack
7. Autopilot     the factory starts the backlog; you watch the board
8. Try it        a story is done → "Preview" runs the app → Accept, or "Ask for changes"
9. Save          "Save to GitHub" whenever you want
```

**A developer with a repository:**

```text
1. hall          → Home → Add project → pick the folder (or clone from GitHub)
2. Memory        the Librarian reads the repo once: architecture, features, conventions
3. Requests      paste a list, or point at a file or a URL with one (an export from any tool)
4. Grooming      the PM and the Lead fold them into the board: new, merged, follow-ups, duplicates
5. Build         the Builder in the background, or you in Claude Code, Codex or Gemini CLI
6. Review        independent review, fixes, the hallmark; PRs merge through the queue
```

## Principles

1. **The CLI is the API; the web is the product.** Every button runs a hall
   command (ADR 0052); every command keeps the agent contract (ADR 0002).
   Nobody *needs* the terminal.
2. **One front door, and a desk behind it.** No request reaches the
   Builder without a story, acceptance criteria and a plan, and the requester
   always talks to the PM or the Lead, who manage how it's addressed.
3. **Orchestrators know everything; workers know their unit.** The PM and
   the Lead see the whole floor; every other run starts clean with a work
   order and asks when it needs more. Every question and answer is logged.
4. **The factory remembers.** What any agent learns about the product or
   the code is written down once, kept fresh, and briefed to the next agent
   that needs it.
5. **Hallmark owns the loop; agents are adapters.** States, journal,
   gates, verdicts and the hallmark don't depend on which agent ran.
6. **Guarantees live in layers every agent passes through:** git, the hall
   CLI, MCP. A harness's own hooks add capture, never the only lock.
7. **Local first.** Git always runs underneath, but a remote is optional.
8. **Plain words for beginners, full power for pros.**
9. **The journal stays append-only** (ADR 0003, 0008).

## 1. One front door

**Decision (ADR 0076): every request goes through the PM and the Lead.**

Today `hall new` already plans (ADR 0068), but `--no-split`, `--title`,
`--issue` and `--branch` skip or weaken it, `hall adopt` skips it, and
feedback after shipping starts work without a story. In 0.4 every channel
becomes a request to the same planner:

| Channel | Becomes |
| --- | --- |
| The web composer, `hall new`, `hall plan` | a plan of one or many requests |
| A list from anywhere: pasted text, a file, a URL (`hall plan --from`) | one request per entry, each keeping its source |
| A GitHub issue (`--issue`, as today) | a request carrying the issue's link |
| "Ask for changes" after a preview, or a comment on a closed story | a request the Lead usually makes a `follow_up` of that story |
| A person's new-scope comment on an open PR | a request the Lead merges into the item or follows up |
| A revert on the base (ADR 0061) | a request to fix forward, linked to the reverted story |
| `hall adopt` (a branch or PR made outside Hallmark) | the PM writes the story and criteria from the diff after the fact, so adopted work has a Definition of Done too |
| An agent's `hall new` from a session | the same plan, applied by the headless rules |

- `hall new "<request>"` stays as the short form of `hall plan` with one
  request. The difference between them is only how many requests go in.
- **Fixes inside the loop are not requests.** Failing checks, review
  findings, rebases, red CI and conflicts stay with the Fixer and Delivery,
  as today. Only new scope goes through the front door.
- **The one way around it is explicit.** `--direct` (replacing
  `--no-split`) makes one item with no PM or Lead; it's recorded on the
  item, shown on its card, and off on the web unless a setting allows it.
- **It must be cheap enough to use every time.** The PM and the Lead start
  from the project memory and the board instead of reading the repository,
  the fast path (ADR 0068) stays for small boards, and `hall stats` reports
  planning cost per request, so the front door can be judged by its numbers.

## 1a. The desk: talking to the PM and the Lead

In a software factory the requester doesn't walk onto the floor and tell a
builder to change something. They talk to the product manager or the lead,
who decide how to address it. Hallmark works the same way.

**Decision (part of ADR 0076): every issue and plan that isn't final has a
conversation with the PM and the Lead, the desk. What you say there is
handled by them, not passed straight to the agent at work.**

### Where you can talk

- **On an issue,** in any state before it's final: triage, backlog,
  development, checks, review, fixing, escalated, held, hallmarked, and
  shipped while its PR is open. On a final issue (merged, closed, dropped)
  the same box sends a new request through the front door, linked to it.
- **On a plan** before it's applied: revise the stories, the grouping, the
  order.
- **On the project,** with no issue: *Ask the factory*. A question is
  answered; anything that asks for work is a request through the front door.
- **On any of the agents' threads** (ADR 0070): a review finding, a
  verifier's check, a Builder's `hall ask`, the PM's grooming question. You
  can reply to each; the reply goes to the desk with that thread attached.

### What you can say, and what the desk can do

You write in your own words. The desk's run (the PM for what and why, the
Lead for how and when; the PM takes it first and hands over when it's about
the how) reads the issue's journal, its threads, the board and the memory,
and returns one structured decision:

| Decision | Effect |
| --- | --- |
| `answer` | a reply, nothing changes ("why is this in review again?", "what does criterion 3 mean?") |
| `ask_back` | the desk needs more from you before deciding |
| `amend` | the issue's story or criteria change (`scope_added`, `criteria_changed`) |
| `reprioritize` | priority, rank or dependencies change, unless you set them yourself |
| `note` | your words go to the next agent on the issue (Builder, reviewer, fixer), once (ADR 0044) |
| `pull_back` | the issue returns to development with a reason, which costs the review done so far |
| `follow_up` / `new` | a new issue through the plan, linked to this one |
| `split` | part of the issue moves to a new issue |
| `hold` / `release` | the issue waits for something, or stops waiting |
| `propose_drop` | dropping it, which only you can confirm |

The desk decides by the issue's state, and says why:

- **Not started (triage, backlog):** amend freely.
- **Building (development):** amend; the Builder, or your harness session,
  is told the added scope at its next step (ADR 0068's mechanism).
- **Frozen commit (checks, review, fixing, escalated, hallmarked):** the
  desk weighs the change against the work it would throw away. By default a
  new requirement becomes a `follow_up`, so the review isn't lost; a
  correction to what's being built (a misunderstanding, a wrong criterion)
  is a `pull_back` or a `note` to the fixer. It states the trade-off in its
  reply.
- **Shipped, PR open:** a `follow_up`, or a `pull_back` through `hall adopt`
  when the change belongs in the same PR.

**Big moves wait for you.** `answer`, `ask_back`, `note` and `amend` on an
issue that hasn't started apply at once. A `pull_back` of a frozen commit, a
`split`, a `propose_drop`, or anything touching another issue is returned as
proposed, with an *Apply* button (`hall talk apply`). Commands never prompt
(ADR 0002).

**What you change directly.** Priority, rank, labels, start, and drop with
a reason stay one click away, as a stakeholder's controls (ADR 0068: a
person's call wins). What the issue *is* (its story, criteria and scope) and
its direction change only through the desk, so the PM and the Lead always
know what was asked and why.

### How it's recorded

- Each message is journaled (`message { from: you | pm | lead, thread }`)
  and each decision too (`desk_decision { decision, applied, reason }`), so
  the conversation is a thread like any other (ADR 0070, kind `desk`) and
  `hall threads` shows it.
- Answered product questions and decisions become memory (decisions layer),
  so the next request doesn't ask again.
- Desk runs are booked to room `front`, roles `pm` and `intake`, under the
  intake budget, on the intake models, with a short timeout.

### Commands

- `hall talk <H-0042 | P-3 | project> "<message>" [--to pm|lead]
  [--thread <id>]` sends a message and returns the desk's reply and
  decision; `--to` picks who reads it first.
- `hall talk apply <decision>` applies a proposed decision.
- `hall talk <id> --list` shows the conversation.

## 1b. The floor: orchestrators and short-lived workers

**Decision (ADR 0086): the PM and the Lead orchestrate; every other role is
a short-lived worker on one unit of work, and agents talk to each other
through the Exchange.**

### The orchestrators know everything going on

The PM (what and why) and the Lead (how, when and who) are the only agents
that see the whole floor and the only ones the requester talks to. They
don't keep one endless conversation, which would grow, drift and cost more
every turn. Their awareness is rebuilt fresh for every run from three
sources:

1. **Facts from hall:** the board (every issue, its state, what it waits
   for, its open questions and threads, its cost), the inboxes and the
   budgets, read from the journal and the index. Facts are never remembered
   by a model, so they're never stale.
2. **The project memory,** core memory first (section 2).
3. **The floor report:** a short running document the Lead rewrites at the
   end of each of its runs: what's in flight and why, risks, decisions
   pending, promises made to the requester. Capped like core memory, kept
   with its history, readable on the web app's floor view. It carries the
   narrative from one orchestrator run to the next.

They run when judgment is needed, not on a timer:

| Event | Who runs | Typically decides |
| --- | --- | --- |
| A request, or a message at the desk | PM, then the Lead | plan, amend, answer (sections 1, 1a) |
| A question addressed to them on the Exchange | the one addressed | answer, or pass it on |
| An issue merged, dropped or escalated | the Lead | start the next issue, re-order, follow up, tell the requester |
| A worker stuck, failing or over budget | the Lead | a note, a split, a hold, or a question to you |
| The daily stand-up (`[floor] standup`, default once a day while work is open) | the Lead | re-plan the backlog, retire stale plans, write the report |

**The loop itself stays in code.** States, transitions, leases, gates,
budgets and the hallmark are decided by hall (ADR 0008, 0014), never by an
orchestrator. If an orchestrator run fails or hits a limit, the deterministic
loop keeps going; only judgment calls wait. The orchestrators act only
through hall commands, as any agent does, so everything they do is journaled
and refusable.

### Workers know their unit of work

The Architect, the Builder, the reviewer, the verifier, the security pass,
the fixer and the Librarian each start **clean**, with a **work order**
built by hall: the unit (an issue, a finding, a design question, an item to
distil), its story and criteria, the paths involved, the memory briefing for
that unit, and the Exchange answers already given about it. Nothing carries
over from another run except through the journal, the threads and memory.
A worker that needs more doesn't guess and doesn't widen its own context: it
asks.

### The Exchange: every role has an inbox

`hall ask` grows from "ask the person" into a question to anyone on the
floor, and the questions and answers together form the **Exchange**: a Q&A
board in the style of Stack Overflow, built from ADR 0069 (consulting the
Lead, answers in the Library) and ADR 0070 (threads).

- **Ask anyone:** `hall ask --to lead|pm|architect|librarian|person
  "<question>" [--item <id>] [--paths <glob>…] [--tags …]`. Each role has its
  own inbox (`hall inbox --role lead`); the person's inbox is today's.
  `hall consult` (ADR 0069) becomes `hall ask --to lead`.
- **Answered in the call when an agent can answer.** A headless run never
  waits on another agent: memory is searched first (answers, decisions,
  learnings), and a good match is returned with no model run; otherwise the
  addressed role answers in a short read-only run, with evidence (file and
  line, a criterion, a recorded decision).
- **Passed up when it can't.** The chain is the factory's: a worker asks
  the Lead about code and the Architect about design; the Lead passes product
  questions to the PM; the PM answers from the criteria and recorded
  decisions, and only a question needing a *new* decision reaches you, in
  your inbox. When nobody can say, the worker goes ahead on a stated
  assumption and records it, as ADR 0069 has it.
- **Reviews stay independent.** The reviewer, the verifier and the security
  pass may read the Exchange's answers about the *base* code, but never ask
  the author's side, and author-side answers never reach a review's briefing
  (ADR 0021, 0069). Their findings are already questions on the Exchange,
  which the fixer answers.
- **Like a Q&A site.** Each question has tags (paths, features, roles),
  answers with evidence, an accepted answer, a reuse count (the upvote:
  how many later runs it answered) and disputes (the downvote: `hall ask
  --dispute <answer> "<why>"`). Answers go stale when their code changes
  and are answered again (ADR 0069). Good answers become memory; the
  Librarian folds often-reused ones into `map` or `rule` entries.
- **Everything is logged.** `asked { from, to, question, item, tags }`,
  `answered { by, source: memory | run | person, evidence }`, `passed {
  to, reason }`, `disputed`, journaled on the asking issue (or the project,
  with none) and shown as threads (ADR 0070, kind `exchange`). Answer runs
  are booked to the asking issue as role `consult`.
- **Bounded.** `[exchange] max_per_run` and `max_per_item` cap the
  questions a worker may ask, so a confused agent asks the Lead for a
  note or a split instead of looping.

### You, on the Exchange

The web app's **Exchange** page shows every question on the floor: search,
filters by role, issue, tag and status, unanswered first. Questions
addressed to you are answered there (or in the inbox). On anyone else's
question you can comment, and as everywhere else, your comment goes to the
desk (section 1a): the PM or the Lead decides what it changes.

## 2. Project memory

The Library (ADR 0021, 0027, 0066) already keeps **learnings** as Markdown
files with frontmatter, searches them with FTS5 (or qmd), briefs reviews
within a token budget, and has the Librarian propose and you approve. It
remembers how to *review* this repo. 0.4 grows it into the memory of the
*project*.

**Decision (ADR 0077): the Library becomes the project memory: layered
Markdown entries, kept fresh by the Librarian, briefed to every role.**

### What it holds

| Layer | Entries | Written by |
| --- | --- | --- |
| Product | `vision` (the brief), personas, glossary, constraints and non-goals | onboarding, the PM, you |
| Features | one entry per feature: what it does, its stories, its main paths | the Librarian, after each item |
| Decisions | product decisions (your answers to the PM), technical decisions (the Architect's notes, ADRs) | the Librarian, from answered questions and design notes |
| Architecture | modules and packages, entry points, data model, how things connect | the Librarian (bootstrap, then after each item) |
| Conventions and pitfalls | today's learnings: `rule`, `false-positive`, `map` | the Librarian, as today |
| History | what shipped: story → feature → files → PR | the journal; the Librarian summarises |

### How it stays easy to maintain

- **One topic per file, plain Markdown,** under the store next to the
  journal (`<git-common-dir>/hallmark/memory/`), readable and editable by a
  person in the web app or any editor. It stays local by default, like the
  Library today. `[memory] commit = true` also keeps it in the repo (through
  records items, as ADR 0066 does for the Library), which suits teams;
  project setup asks whether to, once, and the answer can be changed in
  *Settings* or with `hall config`.
- **Every entry says where it came from and when it was true:**
  `sources` (items, commits, files) and `verified_at` (a commit). When the
  files an entry cites change on the base, it's marked **stale**, and the
  Librarian re-checks it on its next pass instead of trusting it.
- **Small by design.** Each entry has a size cap; **core memory** (vision,
  glossary, the feature index, the architecture summary) has a total cap
  (about 3k tokens) and is always briefed to the PM and the Lead. Everything
  else is retrieved when relevant. The Librarian merges and retires entries
  to stay under the caps.
- **You stay in charge.** Kinds you trust are accepted on their own
  (`[memory] auto_accept`); the rest wait in the inbox as today. Pinning an
  entry keeps it in core memory; your edits are never overwritten (the
  Librarian proposes a change instead). Every version goes to `history/`.

### How it's searched and used

- **Search:** the built-in FTS5 index, as today, plus optional
  embeddings for meaning-based search (`[memory] search = "builtin" |
  "hybrid" | "qmd"`), with filters by layer, kind, feature and path.
- **Briefings per role:** core memory, then what matches the task (the
  request's words, the paths an item touches, the features it links to, the
  PM's related past stories and answers), within each role's token budget.
- **Visible use:** each run records which entries it was briefed, so the
  story page and `hall trace` show what the agent knew, and a wrong entry
  can be fixed at its source.
- **Bootstrapping:** `hall memory bootstrap` has the Librarian read an
  existing repository once, with a read-only run, and write the architecture,
  feature and convention entries, so the first request on an old project is
  already planned with context. A new project starts from its brief.

### Commands

`hall memory [list|show|search|edit|pin|retire|review|bootstrap|stale]`;
`hall library` stays as an alias for the learnings it has today. In the web
app, *Memory* is a page with the layers, search, history and the inbox of
proposed changes.

## 3. Engines: headless runs on any model

Today `runner.rs` builds one command shape, `claude -p … --output-format
stream-json --json-schema …`. The `Runner` trait (`src/runner.rs:456`) and
the `FakeRunner` are the seam.

**Decision (ADR 0078): every headless run goes through an engine adapter.**

- An **engine** takes a `RunRequest` (role, instructions, prompt, working
  directory, `read` or `write` access, a JSON Schema for the answer, timeout,
  budget, a session to resume) and returns a `RunOutcome` (the structured
  answer, usage, a session id, how it ended). Each adapter turns its output
  into **hall's own trace lines**, so `hall trace`, the web app and the
  Gazette don't care which engine ran.

| Engine | Vendor | Runs | Sandbox | Roles in 0.4 |
| --- | --- | --- | --- | --- |
| `claude` | Claude | `claude -p` (today's shape, unchanged) | Claude Code's (ADR 0053) | all |
| `codex` | OpenAI | Codex CLI, headless | Codex's own | all |
| `gemini` | Google | Gemini CLI, headless | Gemini CLI's own | all |
| `api` | Claude, OpenAI, Gemini, or any OpenAI-compatible endpoint (OpenRouter, Ollama, LM Studio, vLLM…) | hall's own small agent loop | hall confines it to read-only tools | read-only roles |
| `fake` | — | the scripted runner | — | tests |

- **Roles pick an engine and a model:** `[roles.<role>] engine, model,
  effort, max_usd, timeout`. Today's keys (`review_model`,
  `[budget.review]`…) stay as aliases for the `claude` engine. A model can be
  written `engine:model` wherever one is asked for.
- **Agents and skills become prompt packs,** rendered per engine (a Claude
  Code plugin agent, Codex and Gemini instructions, or the `api` engine's
  system prompt). `plugin/schemas/` stays the single definition of every
  answer; hall validates every answer against it, whatever produced it.
- **The reviewer from another vendor.** Setup suggests a reviewer on a
  different vendor than the Builder. Independent review is Hallmark's whole
  idea; another vendor's model is more independent still.
- **The `api` engine writes nothing in 0.4.** Writing roles run commands,
  which needs an OS sandbox; until hall has one, they run on a harness with
  its own, or on `api` only with `[sandbox] mode = "off"`, set on purpose and
  shown as a warning everywhere.
- **Usage, prices and limits per engine.** Tokens by kind from each adapter;
  a `[prices]` override for models the table doesn't know (unknown ones are
  counted in tokens only); "out of usage" and rate limits become today's
  pause (ADR 0055). Budgets (ADR 0016) are unchanged.
- **Keys** live in the OS keychain (`keyring`), entered in the web app or
  with `hall engines key set <provider>`; never in config, the journal or a
  sandboxed run's environment.
- **Choosing by evidence.** `hall eval --engine --model` (ADR 0065) scores
  any engine as reviewer on your own reverted PRs.

## 4. Harnesses: development sessions with any agent

Today a development session is seen only through Claude Code's hooks.

**Decision (ADR 0079): the guarantees move to git, the CLI and MCP; native
hooks add capture.**

1. **Git hooks.** `hall init` sets `core.hooksPath` to hall-managed hooks
   that only call `hall hook git-<event>` (`pre-commit`, `post-commit`,
   `pre-push`; one-line `sh` stubs, which Git for Windows runs too). The push
   gate and commit recording hold for every harness and for a person. A
   repo's existing hooks are chained, not replaced.
2. **`hall mcp`,** an MCP server over stdio with the agent commands as
   tools: `new`, `plan`, `status`, `findings`, `propose-ready`, `ask`,
   `attach`, `threads`, `memory search`.
3. **Instructions in every dialect:** one source, written into `CLAUDE.md`,
   `AGENTS.md` and `GEMINI.md`, whichever the project uses.
4. **Native hooks where present:** Claude Code keeps today's plugin; Codex
   and Gemini CLI get adapters for whatever their hooks cover (M0 spike):
   prompt capture, the edit gate, session binding, resuming with an answer.

| | Claude Code | Codex CLI | Gemini CLI | Antigravity, other editors, a person |
| --- | --- | --- | --- | --- |
| Push gate, commits recorded | ✓ | ✓ git | ✓ git | ✓ git |
| hall tools | ✓ CLI + MCP | ✓ MCP | ✓ MCP | MCP where supported, CLI |
| Prompts and turns recorded | ✓ | as its hooks allow | as its hooks allow | — |
| Edit gate before an item exists | ✓ | as its hooks allow | as its hooks allow | caught at commit |

Commits made outside an item are offered for `hall adopt` from the inbox,
which sends them through the front door; nothing is pushed without a
hallmark. `hall setup claude|codex|gemini` installs what each harness takes,
and `hall doctor` and the web app's *Agents* page show which are installed
and signed in.

## 5. Projects

**Decision (ADR 0080): a project is a registered folder that hall can
create, adopt or clone; git runs underneath, a remote is optional.**

- `repos.json` becomes the **project registry** (name, path, `local` or
  `github`, blueprint, created or adopted). Existing entries migrate as
  adopted projects.
- `hall project new <name> [--path] [--blueprint] [--github private|public]`,
  `hall project add <path> | --clone <owner/repo>`,
  `hall project list|remove|rename`. For an added repository, the first
  thing asked is the autopilot level (Assisted by default). A new folder gets `git init` with a
  local fallback identity (or the GitHub noreply address, as rig does),
  `hall init`, and a brief.
- **The projects root is `~/hallmark`** (`hall config set --user
  projects.root`). The web app creates folders only there or in a folder the
  person picked.
- **No fixed templates: the Architect chooses the stack.** A template is a
  ready-made project skeleton (say, a React web app with its test runner and
  linter). Fixed templates force a non-developer to pick a stack they can't
  judge, and age quickly. Instead, a new project starts empty with its brief,
  and the Lead's first item is a **foundation**: the Architect picks the
  stack from the brief and writes a design note, then the Builder scaffolds
  it with the stack's own generator and sets the gates. **Blueprints** are
  optional guard rails for that choice: a short profile per kind of product
  (`web-app`, `api`, `cli`, `static-site`, `mobile`) naming preferred
  stacks, the gates they need and the package registries the sandbox must
  reach. You can name a stack in the brief, and it wins. 0.4 ships
  `web-app`, `api` and `static-site`. Onboarding asks *What are you
  building?*; with no blueprint picked (a mobile app, a game, a desktop tool,
  "I don't know"), the Architect's foundation item first asks a product
  question with two or three stack options and their trade-offs in plain
  words, and you pick one.
- `NOT_A_REPO` and `NOT_INITIALIZED` hint at `hall project new` and
  `hall project add`.

## 6. The tracker

ADR 0068 designed most of it; step 1 is built. 0.4 finishes it and adds what
a tracker needs. The concepts follow Linear's, so they feel familiar; the
design and the words on screen are Hallmark's own.

| Linear | Hallmark | Status |
| --- | --- | --- |
| Project | a plan (`P-0003`), or a parent item with slices | proposed in 0068 |
| Issue | an item: story, criteria, priority, estimate | built (criteria, priority) |
| Sub-issue | a parallel part (ADR 0024) | built |
| Triage | new requests and the PM's questions, before *Apply* | proposed in 0068 |
| Backlog | the `backlog` state, ranked | proposed in 0068 |
| Status | the item's state, grouped into board columns | built |
| Priority | Urgent, High, Medium, Low, None, stored as today's `now` / `next` / `later` plus `urgent` and `none` | built (PM); `prioritize` proposed; two levels **new** |
| Manual order | the rank inside a priority | **new**: `ranked` event |
| Estimate | weighted tokens (ADR 0016), shown as a size (XS–XL) | proposed in 0068; sizes **new** |
| Relations | blocked by / blocks (`after`), related, duplicate of, follow-up of, feature | proposed in 0068; related and features **new** |
| Assignee | the engine or harness that builds it, or you | **new** |
| Comments | the desk: your messages to the PM and the Lead, their replies and decisions, beside the agents' threads (ADR 0070) | **new**: `message`, `desk_decision` |

- **ADR 0068 steps 2 onward:** `hall plan` over lists, plan journals,
  `backlog`, `hall plan answer|prioritize|apply`, `hall start`, `[plan] wip`,
  grooming questions in the inbox, re-planning held stories.
- **New events** `ranked`, `labeled`, `assigned`, `related`, folded like
  the rest; `hall rank|label|assign|relate` (messages and desk decisions are
  in [the desk](#1a-the-desk-talking-to-the-pm-and-the-lead));
  `hall board` returns a whole view (grouped, ordered, filtered) in one reply
  for the web app.

### Requests from anywhere

**Decision (ADR 0081): Hallmark reads lists of requests; it doesn't
integrate with other trackers.**

- `hall plan --from <file|url|->` takes a list in whatever shape it comes:
  Markdown, plain text, CSV or JSON (an export from Linear, Jira, GitHub, a
  spreadsheet, a document). A URL is fetched with a plain HTTP GET, as `curl`
  would (`--header` for a token, never stored); the PM reads the text and
  splits it into requests, each keeping its source (the URL, a line, an
  issue key) on the story.
- The web app's *Add requests* takes the same: paste, drop a file, or a URL.
- Nothing is synced back. `--issue` keeps working for GitHub issues as it
  does today; no new Linear, Jira or GitHub Issues integration is built.

## 7. Running the factory

- **The Builder worker.** A started item that no session claims is built
  by a headless development run on the `builder` role's engine, in its
  worktree, with the story, criteria, rules, skills and memory briefing. It
  commits as it goes, asks with `hall ask` when it must (the question lands
  in the inbox and on the card), and ends with `hall propose-ready`. Same
  sandbox and budgets as the Fixer.
- **Or build it yourself.** *Open in…* opens the worktree in Claude Code,
  Codex, Gemini CLI or your editor. A session that binds to the item takes
  it over; the Builder stops at its next step.
- **Previews and acceptance.** For people who judge by using it: a project
  declares how to run itself (`[preview]`: processes and a URL, the way rig's
  `[processes]` do, written by the foundation item). *Preview* runs a story's
  worktree or the merged base and opens it. *Accept* records your acceptance
  on the story; *Ask for changes* is a request through the front door.
  `[preview] accept = "before_merge"` holds a hallmarked story for your
  acceptance before it merges; the default, `after_merge`, never blocks the
  loop.
- **Autopilot levels per project:**

| Level | Starts items | Says "ready" | Merges |
| --- | --- | --- | --- |
| Manual | you | you | you |
| Assisted (default for added repositories) | you | the agent, when nothing is left to confirm | you, or the merger |
| Autopilot (default for new projects) | the backlog, within the WIP limit | the agent | the merger, or locally |

## 8. The web app

**Decision (ADR 0082): the web app is the main interface, with views and
controls that work like Linear's; it stays local, embedded and offline,
built with vendored Preact and htm, no build step.**

What "like Linear" means here (the interaction model, not its look: the
design, names and icons are Hallmark's own):

- **Keyboard first.** A command palette (<kbd>Ctrl</kbd>/<kbd>⌘</kbd>
  <kbd>K</kbd>) reaches every action. Single keys on the focused issue:
  <kbd>C</kbd> new request, <kbd>/</kbd> search, <kbd>J</kbd>/<kbd>K</kbd>
  move, <kbd>S</kbd> status, <kbd>P</kbd> priority, <kbd>A</kbd> assignee,
  <kbd>L</kbd> labels, <kbd>E</kbd> estimate, <kbd>X</kbd> select,
  <kbd>?</kbd> every shortcut. The mouse does everything too.
- **Views.** List or board for the same issues; group by status, priority,
  assignee, label, feature or project; order by rank, priority, updated or
  cost; filters you can combine; views you save and pin (*My questions*,
  *Building now*, *Urgent*).
- **Peek and inline editing.** An issue opens in a side panel without
  leaving the view; priority, rank, labels and assignee change in place.
  The story and criteria are read-only on screen: a change to them is a
  message to the desk.
- **Bulk actions.** Select several issues and change them, rank them or drop
  them (with one reason) at once.
- **Triage.** New requests and the PM's questions arrive in a triage view;
  you accept, edit, merge or answer before they reach the backlog.
- **Instant.** A change shows at once and is reconciled with the command's
  reply; if hall refuses it, it rolls back with the error's `message` and
  `next`.
- **Calm.** Dense lists, quiet colour, status icons that read at a glance,
  light and dark.

Screens:

- **Home:** your projects, what needs you, what's moving, today's spend.
- **Welcome / onboarding:** machine check, first project, brief, first
  requests, grooming, autopilot. Every step can be left and resumed.
- **Issues:** the list and board views above, by stage (Triage · Backlog ·
  Building · Checks · Review · Fixing · Hallmarked · Shipped · Done); drag to
  start, rank or drop (with a reason).
- **Triage and grooming:** incoming requests, the PM's questions, the
  Lead's plan; *Add requests* (paste, a file or a URL) → the plan → *Apply*.
- **Projects:** plans and their issues, progress, estimates, relations.
- **Issue page:** story, criteria (ticked as evidence arrives), the
  conversation with the PM and the Lead (with a box to write in, addressed to
  either), the agents' threads (each with *Reply*, which goes to the desk),
  activity, live run, diff, findings, checks, cost, preview, accept, PR,
  Gazette, the memory it was briefed. Proposed desk decisions show as cards
  with *Apply*.
- **Ask the factory:** a box on every page (and <kbd>Q</kbd>) to ask the PM
  or the Lead anything about the project, or to ask for something new.
- **Memory:** layers, search, history, stale entries, proposed changes.
- **Factory floor:** today's animated rooms, live.
- **Inbox:** what needs you, with one-click answers.
- **Agents:** harnesses and keys, which engine and model each role uses,
  reviewer eval scores.
- **Settings:** project (gates, shipping, autopilot, WIP, preview, memory
  in the repo), GitHub, budgets, notifications, extensions, daemon, doctor,
  updates.

How it's built:

- **Still every call a hall command** (ADR 0052), with the allowlist widened
  to `project`, `plan`, `talk`, `start`, `rank`, `label`, `assign`, `relate`,
  `memory`, `connect`, `preview`, `setup <harness>` and `engines`. Folders
  only under the projects root or a picked folder; anything that publishes
  (GitHub) asks first.
- **Live:** `GET /api/events` (server-sent events) tails journals and run
  streams; the page reads the commands it needs when something changes.
- **Preact with htm,** about 10 kB, vendored into `src/web/assets/` and
  embedded as today: components without a compiler, no Node in a Rust
  project, works offline and on Windows.
- **Friendly by default:** every empty state says what to do next; errors
  show `message` and turn `next` into buttons; plain words on the happy path.

## 9. Install and first run

- The installers stay (cargo-dist) and end with one line: `hall` to open it.
- **`hall` outside a project** opens the web app on Home or Welcome when
  there's a browser, the terminal app's project list otherwise; off a TTY it
  still prints JSON.
- **`hall doctor` works outside a repository:** git, at least one harness
  or API key, gh (only for GitHub), the daemon, the projects root. Each
  failure names its fix; in the web app, a button where hall can fix it.
- **The lowest bar:** with no harness installed, a person pastes an API key
  and the read-only roles run on `api`; building starts once one harness is
  installed, which Welcome walks them through. Installing git is offered
  (Xcode command-line tools, `winget`), not assumed.
- The daemon starts at login once the first project exists.

## 10. Local, then GitHub

**Decision (ADR 0083): shipping has a target, `local` or `github`.**

- **Local:** a hallmarked commit is merged into the base locally
  (fast-forward, or a merge commit when the base moved), only when its
  hallmark note verifies, as the push gate checks it (ADR 0045). Delivery,
  the merger, the CI watch and the reverts worker stay idle. No `gh` needed.
- **`hall connect github [--create private|public] [--repo owner/name]`:**
  `gh auth login --web` (the page shows the one-time code), create or link
  the repository, push the base, switch `ship`, `update`, `review_comment`
  and `merge` to their GitHub defaults, turn delivery on. *Save to GitHub* in
  the page; it always asks first.

- Existing repos keep working: adopted projects, target `github`, engine

## Risks

- **Planning every request costs tokens.** Memory is the answer, measured
  in M2; if the numbers aren't good, the fast path widens before the front
  door narrows.
- **The orchestrators are a bottleneck if they do too much.** They only
  make judgment calls; the loop runs in code and keeps running when they
  fail. Their runs are short, on the intake models, and measured in
  `hall stats`.
- **Agents asking agents can loop or cost a lot.** Memory answers first,
  questions are capped per run and per issue, and the answer runs are on the
  asking issue's budget.
- **Changing course mid-flight is expensive.** A new requirement on an
  issue in review throws review work away if it's folded in. The desk
  defaults to follow-ups for frozen commits, says the cost of a pull-back
  before proposing one, and waits for you to apply it.
- **Memory that's wrong is worse than none.** Sources, `verified_at`,
  stale marking, your approval for untrusted kinds and visible briefings are
  there for that; the reviewer still reads the code, never memory alone.
- **Harness drift.** Codex and Gemini CLI change fast. M0 fixtures, an
  adapter test suite per engine, and a tested-version check in `hall doctor`.
- **Quality varies by model.** Conservative defaults (a strong reviewer from
  another vendor), the reviewer eval on your own history, shown on *Agents*.
- **Full autopilot for non-developers.** Nobody on their side reads the
  diff, so the gates, the test-first review (ADR 0036), the criteria and
  previews carry the weight; budgets stay on by default.
- **The web app widens what the token can do.** Constrained paths,
  confirmation for anything that publishes, keys never returned to the page,
  the existing token and Host checks (ADR 0052).
- **Windows.** Git hooks through Git for Windows' `sh`, the keychain,
  launching harnesses and previews, gates through `cmd /C`. CI on Windows is
  the check.
- **Scope.** The largest release so far. Each milestone ships value on its
  own: M1 and M3 make Hallmark harness agnostic for today's users, M2 makes
  planning cheaper for them.

## Decisions

1. Web UI: vendored Preact and htm, no build step.
2. First class: Claude, OpenAI and Google Gemini, through Claude Code, Codex
   and Gemini CLI or their APIs; any other model through an
   OpenAI-compatible API. Antigravity through git and MCP.
3. Projects root: `~/hallmark`.
4. No fixed templates: the Architect chooses the stack. Blueprints
   `web-app`, `api` and `static-site` ship in 0.4; with none picked (a mobile
   app or anything else), the Architect offers options and you choose.
5. The tracker's views and controls work like Linear's. No integration or
   sync with Linear, Jira or GitHub Issues: lists come in pasted, as a file
   or from a URL; `--issue` stays as it is.
6. Every request goes through the PM and the Lead, and the requester talks
   to them at the desk on any issue that isn't final; they decide whether to
   answer, change the issue or create a new one.
7. A project memory, grown from the Library: local by default, with
   `[memory] commit` to keep it in the repo, asked once at project setup.
8. Autopilot default for an added repository: Assisted.
9. The PM and the Lead are the orchestrators and know the whole floor;
   every other role is a short-lived worker on one unit of work that asks
   the others through its inbox on the Exchange; everything is logged.
